# 1. Big Picture — How to Think About Graph Problems

A graph problem usually has **three separate decisions**.

```text
Problem statement
      │
      ▼
1. Where is the graph?
   → Graph formulation
      │
      ▼
2. Which graph algorithm fits?
   → DFS / BFS / shortest path / MST / ...
      │
      ▼
3. How should I code it cleanly?
   → Representation + state + traversal template
```

A lot of graph problems do not literally say "You are given a graph."

Instead, you may get:

- cities and roads
- people and friendships
- web pages and links
- tasks and dependencies
- cells in a grid
- states and allowed transitions

The first job is:

```text
objects        → vertices
relationships  → edges
```

Example:

```text
Cities:
1, 2, 3, 4

Roads:
1--2
2--3
3--4
```

Graph view:

```text
(1) -- (2) -- (3) -- (4)
```

# 2. Prerequisite 1 — What Is a Graph?

A graph is commonly written as:

```text
G = (V, E)
```

where:

- `V` = set of vertices/nodes
- `E` = set of edges

Example:

```text
       (2)
      /   \
    (1)   (3)
            \
            (4)
```

Then:

```text
V = {1, 2, 3, 4}

E = {
    (1,2),
    (2,3),
    (3,4)
}
```

Number of vertices:

```text
N = |V|
```

Number of edges:

```text
M = |E|
```

For the graph above:

```text
N = 4
M = 3
```

# 3. Prerequisite 2 — Directed vs Undirected Graph

## 3.1 Undirected Graph

```text
u -- v
```

means:

```text
u can go to v
v can go to u
```

Code:

```cpp
g[a].push_back(b);
g[b].push_back(a);
```

## 3.2 Directed Graph

```text
u → v
```

means only:

```text
u can go to v
```

Code:

```cpp
g[a].push_back(b);
```

Do not automatically add the reverse edge.

# 4. Prerequisite 3 — Graph Representations

The three standard representations are:

1. adjacency matrix
2. adjacency list
3. edge list

Consider this directed graph:

```text
      (1)
     /   \
    v     v
  (2) → (3) → (4)
        ↑
        └────
```

Suppose the directed edges are:

```text
1 → 2
1 → 3
2 → 3
3 → 1
3 → 4
```

So:

```text
N = 4
M = 5
```

## 4.1 Adjacency Matrix

```text
matrix[u][v] = 1
```

if edge `u → v` exists.

```text
       1  2  3  4
    +------------
1   |  0  1  1  0
2   |  0  0  1  0
3   |  1  0  0  1
4   |  0  0  0  0
```

Memory:

```text
O(N²)
```

Edge query:

```text
O(1)
```

## 4.2 Adjacency List

```text
1 → [2, 3]
2 → [3]
3 → [1, 4]
4 → []
```

C++:

```cpp
vector<vector<int>> g(n + 1);
```

Memory:

```text
O(N + M)
```

This is the usual DFS/BFS representation.

## 4.3 Edge List

```text
(1,2)
(1,3)
(2,3)
(3,1)
(3,4)
```

C++:

```cpp
vector<pair<int, int>> edges;
```

Useful for edge-centric algorithms such as Kruskal and Bellman-Ford.

## Comparison

| Representation | Memory | Iterate neighbors of `u` | Typical use |
|---|---:|---:|---|
| Adjacency Matrix | `O(N²)` | `O(N)` | Dense graph |
| Adjacency List | `O(N+M)` | `O(deg(u))` | DFS/BFS |
| Edge List | `O(M)` | `O(M)` | Edge-centric algorithms |

---

# 5. Why Adjacency List Is the Default for DFS

Suppose:

```text
N = 100000
M = 100000
```

Adjacency matrix would need about:

```text
N² = 10^10
```

entries.

Adjacency list stores only actual edges:

```text
O(N + M)
```

So for sparse competitive-programming graphs, adjacency list is the standard choice.

# 6. Prerequisite 4 — Visited Array

DFS must remember which nodes were already explored.

Without it, a cycle like:

```text
(1) -- (2)
 |      |
(4) -- (3)
```

could cause:

```text
1 → 2 → 3 → 4 → 1 → 2 → ...
```

forever.

Use:

```cpp
vector<int> vis(n + 1, 0);
```

Meaning:

```text
vis[u] = 0 → not visited
vis[u] = 1 → visited
```

# 7. DFS — Depth First Search

DFS means:

> Keep going deeper along one available branch before coming back.

Example:

```text
        (1)
       /   \
     (2)   (3)
     /      |
   (4)     (5)
             \
             (6)
```

Possible DFS order:

```text
1 → 2 → 4 → back → 3 → 5 → 6
```

Recursive picture:

```text
dfs(1)
│
├── dfs(2)
│   └── dfs(4)
│
└── dfs(3)
    └── dfs(5)
        └── dfs(6)
```

Core DFS:

```text
dfs(node):

    mark node visited

    for every neighbor:
        if neighbor is not visited:
            dfs(neighbor)
```

Everything later is basically:

```text
basic DFS + extra state
```

# 8. DFS Step-by-Step Dry Run

Graph:

```text
        (1)
       /   \
     (2)   (3)
     / \     \
   (4) (5)   (6)
```

Adjacency list:

```text
1 → [2,3]
2 → [1,4,5]
3 → [1,6]
4 → [2]
5 → [2]
6 → [3]
```

Compact dry run:

```text
Enter 1 → vis[1]=1 → first unvisited neighbor 2
Enter 2 → vis[2]=1 → 1 already visited → go 4
Enter 4 → vis[4]=1 → only neighbor 2 already visited → return
Back at 2 → next unvisited neighbor 5
Enter 5 → vis[5]=1 → neighbor 2 already visited → return
Back at 2 → finished → return
Back at 1 → next unvisited neighbor 3
Enter 3 → vis[3]=1 → 1 already visited → go 6
Enter 6 → vis[6]=1 → neighbor 3 already visited → return
Back at 3 → finished → return
Back at 1 → finished
```

Visit order:

```text
1, 2, 4, 5, 3, 6
```

# 9. Base DFS Template — Undirected Graph

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<vector<int>> g;
vector<int> vis;

void dfs(int node) {
    vis[node] = 1;

    for (int neighbor : g[node]) {
        if (!vis[neighbor]) {
            dfs(neighbor);
        }
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    cin >> n >> m;

    g.resize(n + 1);

    for (int i = 0; i < m; i++) {
        int a, b;
        cin >> a >> b;

        g[a].push_back(b);
        g[b].push_back(a);
    }

    vis.assign(n + 1, 0);

    dfs(1);

    return 0;
}
```

Only graph construction changes:

```cpp
g[a].push_back(b);
```

for edge:

```text
a → b
```

It may be true that:

```text
1 can reach 4
```

while:

```text
4 cannot reach 1
```

# 11. Connected Components

Example:

```text
Component 1          Component 2        Component 3

   (1)---(2)            (6)               (3)
    |     |              |                 |
   (8)---(4)            (7)               (9)
```

One DFS started inside a component visits the whole component.

Therefore:

```text
for every vertex i:
    if i is unvisited:
        new component found
        run dfs(i)
```

Compact dry run:

```text
i=1 → unvisited → component 1 → DFS visits {1,2,4,8}
i=2 → already visited
i=3 → unvisited → component 2 → DFS visits {3,9}
...
i=6 → unvisited → component 3 → DFS visits {6,7}
```

Final:

```text
3 connected components
```

## Code

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<vector<int>> g;
vector<int> vis;

void dfs(int node) {
    vis[node] = 1;

    for (int neighbor : g[node]) {
        if (!vis[neighbor]) {
            dfs(neighbor);
        }
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    cin >> n >> m;

    g.resize(n + 1);

    for (int i = 0; i < m; i++) {
        int a, b;
        cin >> a >> b;

        g[a].push_back(b);
        g[b].push_back(a);
    }

    vis.assign(n + 1, 0);

    int components = 0;

    for (int i = 1; i <= n; i++) {
        if (!vis[i]) {
            components++;
            dfs(i);
        }
    }

    cout << components << '\n';

    return 0;
}
```

# 12. Component IDs and Component Sizes

Sometimes we need more than the count.

We may need:

```text
Which component contains x?
How large is that component?
Are x and y in the same component?
```

Store:

```text
component[u] = componentId
```

Example:

```text
component[1] = 1
component[2] = 1
component[4] = 1
component[8] = 1

component[6] = 2
component[7] = 2

component[3] = 3
component[9] = 3
```

Sizes:

```text
size[1] = 4
size[2] = 2
size[3] = 2
```

## Code

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<vector<int>> g;
vector<int> component;
vector<int> componentSize;

void dfs(int node, int componentId) {
    component[node] = componentId;
    componentSize[componentId]++;

    for (int neighbor : g[node]) {
        if (component[neighbor] == 0) {
            dfs(neighbor, componentId);
        }
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    cin >> n >> m;

    g.resize(n + 1);

    for (int i = 0; i < m; i++) {
        int a, b;
        cin >> a >> b;

        g[a].push_back(b);
        g[b].push_back(a);
    }

    component.assign(n + 1, 0);
    componentSize.assign(n + 1, 0);

    int componentCount = 0;

    for (int i = 1; i <= n; i++) {
        if (component[i] == 0) {
            componentCount++;
            dfs(i, componentCount);
        }
    }

    return 0;
}
```

# 13. Queries: Are x and y in the Same Component?

Once component IDs are known:

```text
x and y connected
⇔
component[x] == component[y]
```

Example:

```text
component[2] = 1
component[8] = 1
component[7] = 2
```

Then:

```text
2 and 8 → YES
2 and 7 → NO
```

Query:

```cpp
if (component[x] == component[y]) {
    cout << "YES\n";
} else {
    cout << "NO\n";
}
```

After preprocessing, each query is:

```text
O(1)
```

# 14. Bipartite Graph — DFS Coloring

A graph is bipartite if every vertex can be colored with two colors such that every edge connects different colors.

```text
color 0 = RED
color 1 = BLUE
```

Valid example:

```text
        R(1)
       /    \
    B(2)   B(3)
      \     /
       R(4)
```

Equivalent partition:

```text
A = {RED vertices}
B = {BLUE vertices}
```

Every edge goes:

```text
A ↔ B
```

Never:

```text
A ↔ A
B ↔ B
```

## DFS coloring rule

If neighbor is uncolored:

```text
color[neighbor] = color[node] ^ 1
```

If already colored:

```text
color[neighbor] must differ from color[node]
```

If equal:

```text
not bipartite
```

## Why an odd cycle fails

Triangle:

```text
      (1)
     /   \
   (2)---(3)
```

Try:

```text
1 = RED
2 = BLUE
3 = BLUE
```

Then edge:

```text
2--3
```

becomes:

```text
BLUE--BLUE
```

Impossible.

## Code

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<vector<int>> g;
vector<int> color;
bool isBipartite = true;

void dfs(int node, int currentColor) {
    color[node] = currentColor;

    for (int neighbor : g[node]) {
        if (color[neighbor] == -1) {
            dfs(neighbor, currentColor ^ 1);
        } else if (color[neighbor] == color[node]) {
            isBipartite = false;
        }
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    cin >> n >> m;

    g.resize(n + 1);

    for (int i = 0; i < m; i++) {
        int a, b;
        cin >> a >> b;

        g[a].push_back(b);
        g[b].push_back(a);
    }

    color.assign(n + 1, -1);

    for (int i = 1; i <= n; i++) {
        if (color[i] == -1) {
            dfs(i, 0);
        }
    }

    cout << (isBipartite ? "YES" : "NO") << '\n';

    return 0;
}
```

# 16. Cycle Detection in an Undirected Graph

Cycle example:

```text
(1) -- (2)
 |      |
(4) -- (3)
```

Cycle:

```text
1 → 2 → 3 → 4 → 1
```

In an undirected graph, a child always sees its parent again.

So we need:

```text
parent
```

# 17. Why Parent Is Necessary

Graph:

```text
(1) -- (2) -- (3)
```

DFS:

```text
dfs(1, -1)
  → dfs(2, 1)
```

At node `2`, neighbor `1` is already visited.

But that is not a cycle.

It is simply the edge we came from.

Correct rule:

```text
visited neighbor AND neighbor != parent
→ cycle
```

Visual:

```text
No cycle:

(1) ---- (2) ---- (3)
          ↑
        parent
```

Cycle:

```text
(1) ---- (2)
 |        |
(4) ---- (3)
```

If DFS reaches:

```text
1 → 2 → 3 → 4
```

and node `4` sees visited node `1`, then:

```text
1 != parent(4)
```

so a cycle exists.

## Code

```cpp
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<vector<int>> g;
vector<int> vis;
bool cyclePresent = false;

void dfs(int node, int parent) {
    vis[node] = 1;

    for (int neighbor : g[node]) {
        if (!vis[neighbor]) {
            dfs(neighbor, node);
        } else if (neighbor != parent) {
            cyclePresent = true;
        }
    }
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    cin >> n >> m;

    g.resize(n + 1);

    for (int i = 0; i < m; i++) {
        int a, b;
        cin >> a >> b;

        g[a].push_back(b);
        g[b].push_back(a);
    }

    vis.assign(n + 1, 0);

    for (int i = 1; i <= n; i++) {
        if (!vis[i]) {
            dfs(i, -1);
        }
    }

    cout << (cyclePresent ? "Cycle exists" : "No cycle") << '\n';

    return 0;
}
```

# 18. Cycle Detection Dry Run

Graph:

```text
(1) -- (2)
 |      |
(4) -- (3)
```

Dry run:

```text
Enter 1, parent=-1
→ visit 2

Enter 2, parent=1
→ neighbor 1 is parent → ignore
→ visit 3

Enter 3, parent=2
→ neighbor 2 is parent → ignore
→ visit 4

Enter 4, parent=3
→ neighbor 3 is parent → ignore
→ neighbor 1 already visited
→ 1 != parent(4)
→ cycle found
```

The key line is:

```cpp
else if (neighbor != parent)
```

# 19. Complexity

For adjacency-list DFS:

```text
Every vertex is processed once.
Every edge is examined a constant number of times.
```

Therefore:

```text
Time = O(N + M)
```

Memory:

```text
Adjacency list = O(N + M)
Visited/state  = O(N)
Recursion      = O(N) worst case
```

For undirected graphs, each edge appears twice in adjacency lists:

```text
u → v
v → u
```

so total neighbor entries are `2M`, but:

```text
O(N + 2M) = O(N + M)
```

# 20. Common Mistakes

### 1. Forgetting reverse edge in undirected graph

Need:

```cpp
g[a].push_back(b);
g[b].push_back(a);
```

### 2. Calling DFS only from node 1

That only explores node 1's component.

For disconnected graphs:

```cpp
for (int i = 1; i <= n; i++) {
    if (!vis[i]) {
        dfs(i);
    }
}
```

### 3. Marking visited too late

Mark immediately:

```cpp
vis[node] = 1;
```

### 4. Bipartite: checking only one component

Loop through every vertex because another disconnected component might contain an odd cycle.

### 5. Cycle detection without parent

Wrong:

```cpp
if (vis[neighbor]) {
    cyclePresent = true;
}
```

Correct:

```cpp
if (vis[neighbor] && neighbor != parent) {
    cyclePresent = true;
}
```

### 6. Using undirected cycle logic for directed graphs

Directed cycle detection needs a different DFS-state model.

# 21. Pattern Recognition Checklist

Ask:

```text
1. What are the vertices?
2. What are the edges?
3. Directed or undirected?
4. Weighted or unweighted?
5. One component or possibly many?
6. What extra information must DFS maintain?
```

Then map:

```text
Reach all nodes?
→ basic DFS

Count disconnected groups?
→ connected components

Need group id?
→ component labeling

Need group size?
→ component-size accumulation

Need same-component queries?
→ compare component ids

Need 2-coloring?
→ bipartite DFS

Need cycle in undirected graph?
→ DFS + parent
```

# 22. Final Mental Model

Do not memorize several separate DFS programs.

Memorize one skeleton:

```text
                 DFS(node)
                    │
          ┌─────────┴─────────┐
          │                   │
      mark state        inspect neighbors
                              │
                    if unvisited → DFS
```

Then attach extra state:

```text
Basic DFS
    │
    ├── + component id
    │      → connected components
    │
    ├── + component size
    │      → component sizes
    │
    ├── + color
    │      → bipartite graph
    │
    └── + parent
           → undirected cycle detection
```

Reusable graph workflow:

```text
Graph formulation
      ↓
Adjacency list
      ↓
DFS skeleton
      ↓
Add exactly the state the problem asks for
```

This foundation leads naturally into:

```text
DFS timestamps
subtree sizes
topological sorting
bridges / articulation points
strongly connected components
tree DP
Euler tours
```
